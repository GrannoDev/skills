# Climb

1. Read the request and project instructions. For Jira, use available integrations or authenticated access to read the ticket and relevant acceptance criteria; never guess its contents. If essential requirements or access are missing, ask for them. Inspect the working tree and preserve unrelated changes.
2. Inspect the affected code and setup. For a bug, reproduce it before fixing; if reproduction is blocked, report why. For an applicable UI change, capture a baseline screenshot before editing, or record why it was unavailable.
3. Implement the smallest clean solution and relevant tests. Do not add code comments. Follow project conventions and do not alter unrelated work.
4. Run the installed `deslop` skill on the work from this task. If unavailable, run the bundled [deslop instructions](references/deslop.md) instead and say so in the handback. Preserve behavior and unrelated changes.
5. Run relevant tests and exercise the changed behavior after deslop. For applicable UI changes, capture a matching after screenshot at native resolution with the same viewport, state, and representative data as the baseline. Save evidence outside the repository or in its designated artifact directory; exclude secrets and personal data.
6. For work testable through an application, start it using the project's documented development setup and keep it running for handback. Expose only to the tailnet: prefer binding to the Jetson's Tailscale IP; use Tailscale Serve only if it will not overwrite existing configuration. Never use Funnel, disable authentication, or expose sensitive data. Prepare a ready-to-test scenario in the development or test environment: create or safely reuse the domain entities needed to exercise the change, with the exact relevant configuration, lifecycle state, relationships, representative data, and test-account permissions. This applies to any entity type, not just a particular feature or domain. Use synthetic data and authorized setup paths; do not modify production or unrelated records. Verify the supplied account can access the prepared scenario, and leave it at the starting point for the recipient to test without creating or configuring prerequisites. If setup is blocked, report the missing prerequisite rather than handing back a generic link as ready to test. Verify the actual URL responds on the Tailscale endpoint and exercise the relevant flow where possible; distinguish local verification from access verified on another device. For UI work, generate a scannable QR code for that exact URL locally, without a third-party service, and include the image or its accessible artifact path.
7. Require an independent agent to verify the final implementation after deslop and setup. Give it the request, acceptance criteria, changed paths, test target, prepared scenario and entity identifiers, and safe access details; ask it to exercise the changed behavior itself using the appropriate browser, API, or other interface, including the reported bug or feature flow. Code review or reading test results alone is not verification. Require its steps, expected and observed results, evidence, and pass/fail or blockers. Fix failures and have an independent agent verify the updated behavior again; repeat until it passes. Do not change the implementation after the passing verification without repeating it.
8. Before any handback, including a blocked one, remove temporary files, test data, and helper processes created by this task or its verifier. Preserve the running application, the prepared handback scenario and its required test data and accounts, requested screenshots and QR code, necessary verification evidence, and all pre-existing or unrelated data. After verification, reset or recreate any scenario consumed or altered by testing so the recipient can start the documented flow; verify its readiness again before handback. Never delete anything unless its ownership and safety are clear. Check the working tree and report any cleanup blocked or intentionally retained artifacts. If cleanup changes the implementation, repeat independent verification.
9. Finish using the [handback template](references/handback.md) only after independent verification passes. Whenever handing back an application link, include the credentials needed to try it and a numbered, step-by-step guide from opening the link through exercising the changed behavior, with the expected result. Use authorized test-account credentials only; never disclose production credentials, tokens, or personal secrets. If credentials cannot safely be shared, give exact sign-in or credential-retrieval instructions instead; if no sign-in is required, say so. If another agent or required access is unavailable, stop and report the work as blocked, what was attempted, and what is needed; never substitute self-verification or claim completion. Never invent a URL, screenshot, QR code, test result, or verification.
